## Status after review

Excellent run: four fixes approved and proven inside the live AI loop. A review of the results (and an external critique) led to these changes. All are in code with tests; **feature freeze from here.**

- **Criteria could not fail.** The model wrote `error_rate > 0` almost everywhere, so one failed request would confirm a hypothesis. Code now raises any threshold that baseline noise could reach (errors ≥ max(5× baseline, 1%); p95 ≥ 5× baseline and ≥ 2× the worst normal p95). Re-checking all 7 live verdicts with these floors: **all still confirmed**, because the observed impact was far above them.
- **The code can refute, and now says so.** The same criteria are evaluated on every after-fix re-run. **Frontend and catalog: refuted after the fix.** Cart: still confirmed on latency (p95 2.7 s). The Analyst reports this.
- **Scores no longer saturate.** Errors and latency now use square-root scales (5% errors cost 13, 50%+ cost 40; +1 s costs 8, +10 s costs 25). Previously 12% errors and a total outage scored the same. The [scoreboard](../../evidence/SCOREBOARD.md) is regenerated: frontend 18 → 96, cart 31 → 78, catalog 70 → 99, Redis 13 → 50.
- **Remediation re-proposed the Redis fix while it was live.** `remediation.applied()` now dry-runs each catalog patch on the server; if it would change nothing, the fix is already in place and the model is never offered it.
- **The AI's report claimed Redis data loss although the integrity checks passed**, and its table disagreed with the verdict numbers (it used only the in-fault window). The Analyst now uses the same observation as the verdict, shows how many criteria held, flags data-loss claims the integrity checks contradict, and keeps each experiment's log lines to its own time window (the frontend section was quoting a cart error from a later experiment). If the model returns invalid JSON, the measured part of the report is still written, and the raw reply is saved.
